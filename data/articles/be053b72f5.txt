In this episode, Christopher "CRob" Robinson, CTO of OpenSSF, Akrites and Chief Security Architect of the Linux Foundation, explores the state of software supply chain security amid multiple security incidents and explains how tools like Scorecard, the Security Baseline framework, and SLSA help harden software.
The conversation also delves into the impact of global cybersecurity regulations like the EU Cyber Resilience Act (CRA), digital sovereignty, and the role of AI in software engineering. Chris shares insights on OpenSSF's Cyber Reasoning System, practical guardrails for AI-assisted development, and how open-source projects are adapting AI contribution policies.
Key Takeaways
- Frameworks like OpenSSF’s Security Baseline translate compliance mandates (EU CRA, NIST SSDF) into 41 practical, verifiable controls for maintainers and enterprise consumers alike.
- SLSA (Supply Chain Levels for Software Artefacts) complements Security Baseline by hardening development infrastructure, CI/CD pipelines, and source repositories across maturity levels.
- The EU Cyber Resilience Act (CRA) is setting a global benchmark for consumer-focused software security regulation, encouraging international harmonisation across regions like the UK, India, Japan, and Australia.
- AI tools accelerate software creation but require structured harnesses, such as OpenSSF's Cyber Reasoning System and upcoming security skills, to enforce established software engineering discipline.
- Open-source software and local-first data paradigms are essential for digital sovereignty, enabling organisations to retain data control and avoid vendor lock-in.

Christopher Robinson: First, I would highlight our Security Baseline, which represents the next evolution of Scorecard. The Baseline includes 41 recommended security controls and practices. We analyzed global regulations like the EU Cyber Resilience Act (CRA) and frameworks like the NIST Secure Software Development Framework (SSDF) to curate a practical list of actions for project maintainers and consumers.
It combines technical configurations—such as enabling branch protection settings on source code repositories—with organizational controls, like publishing a clear security policy or documenting contributor onboarding and maintainer progression paths.
The Security Baseline is structured across three maturity levels. Level 1 is the most straightforward, roughly equivalent to a mid-range Scorecard score, and takes an experienced developer about two hours to implement. It focuses heavily on documentation. While non-profit open-source maintainers are generally not legally bound by cybersecurity regulations like the EU CRA, downstream manufacturers and governments care immensely about compliance.
The EU CRA explicitly exempts open-source maintainers who do not profit from their work. However, commercial consumers must comply. The Security Baseline translates complex regulatory requirements—from the EU CRA, US Executive Orders, and Japanese legislation—into accessible, practical steps for maintainers without requiring them to digest raw legal texts.
By offering a tiered implementation aligned with modern security practices, the Security Baseline makes projects more attractive to downstream consumers. This increased visibility helps attract more contributors, users, feature requests, and code reviews to strengthen the project.
The second framework I recommend is SLSA (Supply Chain Levels for Software Artifacts), which addresses supply chain provenance, pedigree, and integrity. While Scorecard and Security Baseline focus on code and process quality, SLSA secures the underlying infrastructure—including IDEs, developer workstations, source repositories, CI/CD pipelines, and distribution systems.
SLSA defines progressive levels of maturity to harden development infrastructure. By pairing process-oriented frameworks like Scorecard or Security Baseline with SLSA, organizations can verify how software moves securely through the supply chain and assess infrastructure resilience.
