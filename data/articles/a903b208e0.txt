Written by: George Manuelian, Chief Strategy Officer, RapidFort
The modern software stack has become an iceberg. The application code customers and security teams see at the surface is only a small portion of what is being shipped. Beneath it sit operating systems, frameworks, libraries, packages, and transitive dependencies, with much of it drawn from open source or third parties.
As AI accelerates software development, that hidden complexity has become an even more critical security challenge.
For business and technology leaders, the question is no longer simply how many vulnerabilities exist. It is where does meaningful risk live, which vulnerabilities can be exploited in our environment, and how we can reduce that risk without turning developers into full-time vulnerability managers.
The answer requires a fundamental shift from vulnerability accumulation to continuous software resilience.
First step: Recognizing composition of modern software
The typical containerized stack is layers of base operating system software, packages, libraries, language frameworks and dependencies, and the application itself. The application a company writes may represent only a small portion of what it ultimately ships.
That is important because vulnerabilities multiply. A vulnerable package in a base image is not necessarily one vulnerability in practice; it can be replicated across every application and container that uses that image.
In light of this, executives should ask a different question of their security programs: How much of the reported risk is relevant to the way our software operates? Traditional scanning frequently identifies the presence of a vulnerable component without establishing whether that component is loaded, executing, reachable or exposed.
A software bill of materials (SBOM) identifies what exists; a runtime bill of materials (RBOM) can pinpoint what is actually being used. That distinction can dramatically reduce noise.
For example, in the real world from a customer, an NGINX image containing 152 packages and 48 CVEs had only 47 packages actually running in the application. More than 80% of the software was not being exercised. The lesson is not that every unused package is harmless, but that security teams need operational context before assigning remediation urgency.
This is also why severity alone has become an inadequate basis for prioritization. A high or critical Common Vulnerability Scoring System (CVSS) score can command attention, but the business question is whether the vulnerable code is relevant and exploitable in the environment.
There are four contextual factors increasingly shaping remediation decisions: Whether a vulnerability is exposed, whether it is a known exploited vulnerability, whether exploitation is automatable, and whether exploitation would have meaningful technical impact.
The shift from severity to exploitability and reachability is important because it changes the operating model. Instead of asking engineering teams to chase the largest number on a scanner dashboard, leaders should ask whether the organization has enough visibility to determine what is running, what is reachable, and what is exposed.
As a result, security becomes a business-risk exercise rather than a race to close tickets.

Hardening is the important next step
Hardening should not mean merely passing a configuration benchmark. It should also mean removing software and functionality that the application does not need
. Every unnecessary library, shell, package manager, build utility, or default component increases the amount of software that must be maintained and potentially gives an attacker additional tools if a container is compromised.
Runtime profiling is a proven approach for identifying these unused components and removing them systematically.
AI makes this discipline more important
AI-assisted development can rapidly generate code and pull in packages, but developers may not always know which dependencies were introduced or whether they remain necessary as the application evolves.
For example, a development environment in which developers may have to ask the AI system which Python version or packages were used because the model generated much of the implementation is a warning sign for governance.
Speed of development cannot come at the expense of knowing what is being shipped.
No one is going to slow AI development. The answer is to put security controls into the pipeline so developers do not have to perform every security task manually. Clean, curated base images; runtime profiling; removal of unused components; vulnerability context; and automated rebuilding can become repeatable parts of CI/CD.
The objective is to make the secure path the default path.
Introducing Zero Trust software architecture
Zero Trust has traditionally been associated with network access and identity. But when organizations continuously ingest open source and third-party software, they also need to question the software entering their environments.
Software should be verified, trusted components should be maintained in controlled registries, and the software should be continuously evaluated as it moves through development, testing and production – following the common principles of Zero Trust.
This represents a meaningful change in how software supply chain security should be managed. The goal should not be a perfect vulnerability dashboard.
The goal should be a development system that continuously produces software with less unnecessary code, fewer meaningful vulnerabilities, and a smaller attack surface.
For example, one customer reduced an initial 5,286 findings to three unresolved vulnerabilities within 48 hours by combining profiling, curated images, and removal of unused components.
The strategic lesson learned
Vulnerability remediation should become a manufacturing process, not a recurring emergency. If organizations wait until a scanner produces a massive backlog, they have already allowed complexity to become technical debt.
If instead they control what enters the software supply chain, understand what actually runs, prioritize based on reachability and impact, remove what is unnecessary, and continuously rebuild from cleaner components, security becomes part of software production itself.
This approach also changes the conversation between security and engineering. Developers should not be expected to fix every finding simply because a scanner found it. They need context, automation and a clear understanding of which risks require action.
Security leaders need visibility into runtime behavior and the ability to distinguish a theoretical exposure from a vulnerability that can actually affect the business.
The future of software security in the AI era
The future of software security belongs to organizations that manage complexity continuously. AI will accelerate development, it’s a given. Open source will remain foundational, that’s understood. Neither trend is going away, nor should it of course.
But both make it more important to establish disciplined software intake, strong supply-chain controls, runtime visibility, effective hardening, and automated remediation.
Ultimately, the objective is not simply to reduce the number of CVEs on a report. It is to build software that contains less unnecessary functionality, relies on cleaner components, exposes fewer opportunities to attackers, and can be continuously refreshed without overwhelming those responsible for delivering it
. Software supply chain security works best when profiling, verification, clean images, and removal of unused components are built directly into the pipeline.
The executive mandate for the AI era must stop treating vulnerability management as a downstream cleanup exercise. Build security into the way software is assembled, tested and deployed.
When continuous remediation becomes part of the normal development life cycle, organizations can move faster without accepting vulnerability volume as an unavoidable cost of innovation.
