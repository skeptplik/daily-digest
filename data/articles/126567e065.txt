A critical vulnerability dubbed Java4Shell in OpenJDK, the open-source implementation of Java, can allow unauthenticated attackers to remotely execute code on popular enterprise applications, including Jenkins, Atlassian Jira, Confluence, and Keycloak.
Java is one of the most widely used programming platforms in the world, powering enterprise applications, web services, financial systems, and critical business infrastructure.
Because many applications use the same Java runtime, vulnerabilities in its core components can affect a wide range of different and unrelated applications.
The vulnerability, tracked as CVE-2026-114938, is a memory-corruption flaw in Java's hardware-accelerated Base64 decoding functionality that can be exploited to disclose sensitive information from memory or achieve remote code execution (RCE).
Security researchers at Calif, who disclosed the flaw on Tuesday, rated it critical with a CVSS 4.0 score of 9.2, while Oracle assigned it a lower severity rating of 8.1 (High) using CVSS 3.1.
Java4Shell affects OpenJDK 17.0.6 and later, as well as Java distributions built from the affected code, including Oracle Java SE, Amazon Corretto, Eclipse Temurin, Microsoft Build of OpenJDK, Azul Zulu, and Red Hat OpenJDK.
The vulnerability stems from a bug in Java's Base64 decoder, which processes encoded data commonly found in authentication, file uploads, and network communications.
According to Calif, specially crafted Base64 data can cause the decoder to overwrite portions of Java's memory, potentially allowing attackers to steal sensitive information or execute malicious code.
The researchers say that the memory corruption can be triggered with just 64 "A" characters followed by a single equals sign (=):
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
Older OpenJDK 17 versions require 128 "A" characters followed by the equals sign.
The flaw only affects a hardware-accelerated decoding function used on certain x86-64 processors that support AVX-512 instructions.
The researchers have been able to exploit this bug to perform remote code execution against a variety of widely used Java applications running with their default configurations, including:
- Unauthenticated RCE: Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins, and PingFederate.
- Authenticated RCE: Apache Kafka Broker, Apache Solr, Elasticsearch, Gerrit, and Spinnaker.
Calif was also able to exploit the flaw in sample applications built using the Apache Struts and Spring Boot frameworks.
However, the researchers said Java4Shell does not have a universal exploit, and attackers must find an application-dependent way to deliver malicious Base64 data to the vulnerable decoder to achieve code execution.
The vulnerability also requires the affected hardware-accelerated AVX-512 decoding function to be used, which depends on supported x86-64 processors with AVX-512 VBMI capabilities.
Calif says researcher Quang Luong discovered the flaw using OpenAI's Codex AI coding assistant, which helped identify the vulnerability during an audit of OpenJDK's internals.
According to the researchers, Luong discovered the flaw in approximately one hour and developed an initial working exploit in another two hours, at a total AI usage cost of less than $200.
The company says AI agents also helped develop additional application-specific exploitation chains.
Calif has published a proof-of-concept demonstrating the memory corruption but has not released the weaponized exploits used against the affected enterprise applications.
Oracle released patches for CVE-2026-114938 on November 17 as part of its November Critical Security Patch Update, which addresses 655 security vulnerabilities across its product portfolio.
The company recommends that customers apply the available security patches as soon as possible.
For those who cannot immediately update their Java implementations, Calif recommends disabling the vulnerable hardware-accelerated Base64 functionality by launching OpenJDK with the -XX:-UseBASE64Intrinsics option.
Alternatively, administrators running Java on x86-64 systems can use -XX:UseAVX=2 to disable AVX-512 instructions.
However, these workarounds are temporary mitigations, and all developers should update the Java runtimes to the latest version.
